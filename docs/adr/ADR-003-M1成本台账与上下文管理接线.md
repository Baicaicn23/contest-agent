# ADR-003：M1 成本台账与上下文管理的接线方式（计量代理 + 框架压缩）

- **状态**：已接受（2026-09-30，v2/M1）
- **背景**：v2 规划（开发文档 §12）M1 = 成本台账 + 上下文管理。开工前实测发现 AgentScope 2.0.8 已内置上下文压缩（`ContextConfig`：阈值比例 + LLM 结构化摘要 + 截断兜底），与规划中"手写 compact"的预设冲突——需要决定哪些自研、哪些用框架。原则沿 ADR-002：**框架已验证的能力不自研**。

## 决策

1. **成本记账走"两条通路各设一个卡口"**：
   - 结构化调用通路（识别）：`CostMeter`（应用层服务，记账+预算熔断）注入 `OpenAiCompatLlm`——token 用量在 SDK 响应里，只有适配器看得见；
   - agent 循环通路（生成/备考路径）：`MeteredChatModel` 代理包住框架模型客户端，拦截 `__call__` 完成熔断前查 + 调用后记账（代理模式，类比 Java 动态代理/AOP；框架按鸭子类型调用，对代理无感）。
2. **上下文压缩用框架的 `ContextConfig`，不自研 compact**。我们做的只有三件：把阈值配置透传给 Agent；自研框架没有的**工具结果统一截断**（`_with_truncation` 外壳，所有工具经统一入口注册）；离线验证自动压缩真实发生（假模型小窗口场景）。
3. **预算熔断只设一个收口点**：`CostMeter.precheck()` 在"下一次调用发出前"拦截；打穿预算的当前调用照常入账（钱已花、响应已到手，扔掉是浪费）。识别用例捕获熔断后保留已完成的结果并入库（"熔断不是清算"）。
4. **计价规则集中一处**：单价进 config.yaml 模型档案（`input_price_per_m`/`output_price_per_m`，元/百万 token），`compute_cost_yuan` 纯函数计算；没配单价记 token 不算钱，账单如实显示"未知"。

## 被否决的选项

| 选项 | 否决理由 |
| --- | --- |
| 手写 CompactingMemory（pi 式消息双层分离） | 框架内置压缩（自动触发 + 结构化摘要 + 截断兜底）已覆盖同一需求；自研 = 重新背 ADR-002 之前"质量责任在自己"的包袱。pi 的双层分离作为对照学派记入讲解文档，M2 会话存档再做实质借鉴 |
| 装饰器包 `LlmPort` 记账 | 装饰器拿不到 SDK 响应里的 usage（`complete_structured` 只返回解析后的 dict），要记准就得重写调用逻辑——得不偿失 |
| 事后汇总记账（读 `agent.state` 的 usage） | 只能事后报警不能中途熔断，预算闸门验收（"超预算任务被拦截"）不达标 |
| `record()` 记账后超限即抛异常 | 响应已到手、钱已花，抛异常把成果扔掉；统一收口到 `precheck()` 语义更干净 |
| 费用精确审计（存成交价快照） | 当前单价配置静态适用，误差可忽略；真有调价对账需求再做（YAGNI） |

## 已知缺口（刻意接受）

框架做上下文压缩时内部另发的摘要调用不经过 `MeteredChatModel.__call__`，那几笔 token 暂不进台账（压缩低频，量小）；`generate_structured_output` 透传路径同理。若后续审计发现缺口显著，在代理层补拦截即可。

## 后果

- 正面：用例层零改动获得记账+熔断（横切关注点由装配根统一注入）；换模型/调价改配置即可；台账同时成为模型路由（验收"台账可证"）与后续 M2 记忆/评测的度量衡。
- 负面：`MeteredChatModel` 依赖框架"鸭子类型调用模型"的实现细节（升级框架需回归 `test_m1_cost_context.py` 的压缩与代理测试）；压缩摘要调用不入账（见上）；离线压缩测试的窗口参数需要精心卡位（三个数值约束，已在测试 docstring 说明）。
- 实测验收：84 离线 + 4 live 全绿；真实识别 10 条通知后 `sai cost --task identify --today` 回答 ¥0.0173/4 次；`BUDGET_PER_TASK_YUAN=0.001` 真实熔断演示通过（已入库成果保留）。
