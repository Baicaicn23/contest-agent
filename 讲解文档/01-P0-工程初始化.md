# 01 · P0 工程初始化：uv、洋葱四层、装配根、settings

> P0 交付了什么：一个能起 FastAPI `/health`、能跑 `sai` 命令、3 个测试全绿的**空骨架**。它没有业务功能，但它把"未来所有代码住哪、依赖往哪流"定死了——这是整个项目最便宜纠正错误的时候。

## 1. uv：为什么不用 pip

`uv` 是 Rust 写的 Python 包管理器，一条 `uv sync` 完成：读 `pyproject.toml` → 解析依赖 → 建 `.venv` → 装包（含项目本身，editable 模式）。对比 pip + venv 手工三件套：快一个数量级，且锁版本可复现。

本项目日常只需四条命令：

```bash
uv sync                # 装依赖（pyproject.toml 变了之后跑）
uv run pytest          # 跑测试（uv run = 在项目 venv 里执行）
uv run sai serve       # 起 FastAPI（默认 127.0.0.1:8000）
uv run sai model       # 查看模型档案
```

两个 `pyproject.toml` 细节值得看懂：

- `[project.scripts] sai = "contest_agent.presentation.cli:main"` —— 把 `sai` 命令注册进 venv，装完即用；
- `[dependency-groups] dev` —— pytest/httpx 只进开发环境，不污染生产依赖。

## 2. 洋葱四层：依赖永远向内

```
presentation ──► application ──► domain ◄── infrastructure
（HTTP/CLI）      （用例/harness）  （实体+端口）   （实现端口）
```

规则只有一条：**依赖箭头只能指向内层**。`domain/` 是洋葱芯，零外部依赖——它不知道 FastAPI、不知道 SQLite、不知道 DeepSeek，只声明"我需要有人会爬通知（NoticeSourcePort）、会存比赛（CompetitionRepositoryPort）、会调模型（LlmPort）、会搜索（SearchPort）"。

打开 `src/contest_agent/domain/ports.py` 看一眼：四个 `Protocol`，就是四份"能力招聘启事"。谁来实现？`infrastructure/`。这就是**依赖倒置**：业务不依赖实现，实现依赖业务的接口。P3 你会亲手练一次——仓储类实现 `CompetitionRepositoryPort`，测试时换成内存假仓储，业务代码一行不改。

**判断自己有没有写反**：如果 `domain/` 里的文件 import 了 `fastapi`/`sqlalchemy`/`openai` 任何一个，就是写反了，立刻停下来想。

## 3. composition.py：唯一知道具体实现的地方

```python
def build_app() -> FastAPI:
    settings = load_settings()
    # P1: crawler = RequestsNoticeSource(...)
    # P2: llm = OpenAiCompatLlm(...)
    # P3: repo = SqliteCompetitionRepository(...)
    return create_app(settings)

app = build_app()
```

装配根的纪律：**对象图的组装只发生在这里**。其他模块缺什么，靠构造参数传进来（依赖注入），而不是自己 `import` 一个具体类 new 出来。好处：换实现只改这一个文件；测试里可以传假实现。

现在看它很"空"，这正是 P0 的目的——**先把管子铺好，水（业务）后通**。注释里的 P1-P3 就是未来三条管子的接口位置。

## 4. settings.py：环境优先配置

优先级：**环境变量 > config.yaml > 代码默认值**。

为什么密钥只存"环境变量名"（`api_key_env: DEEPSEEK_API_KEY`）而不是密钥本身？因为 config.yaml 会进 git——**进了 git 的东西就等于公开了**。真实密钥放 `.env`（已被 .gitignore 排除），部署环境直接设环境变量，代码一行不用改。

`@lru_cache` 在 `load_settings()` 上：配置整个进程只读一次。P3 换数据库就是设 `DATABASE_URL` 环境变量，验收项"换内存库测试仍通过"靠的就是这一层。

踩的一个小坑（留作记录）：config.yaml 里模型档案的键名就是档案名（`models: deepseek: {...}`），最初 `ModelProfile` 又要求 `name` 字段，pydantic 校验直接炸。修法是在 `load_yaml_config` 里把键名注入 `profile.setdefault("name", name)`——**配置文件别让用户写重复信息，程序替他补**。

## 5. 验收是怎么过的

开发文档 §9 写 P0 验收："uvicorn 起 /health 返回 ok；sai --help 可用"。落到 `tests/test_p0_bootstrap.py` 三个测试：

1. `test_health_returns_ok` —— `TestClient(build_app())` 打 `/health`，验 status=ok 且 active_model 已接通（证明装配根真的在干活）；
2. `test_yaml_config_parses` —— 配置能解析、active_model 指向存在的档案、**每个源 request_interval ≥ 1.5s（把爬虫合规写成测试！）**；
3. `test_active_profile_resolves` —— 密钥确实只存环境变量名。

**要点：验收标准 = 可执行测试，不是"我试过没问题"。** 手工验证只做了额外一次（起真服务 curl /health），因为 TestClient 不验证真实网络栈。

## 6. git 分支流

```
main ──► docs: v1.4 文档体系 ──► merge feat/p0-init ──► （P1 从这里再开新分支）
                                        │
                                        └── feat/p0-init: feat: P0 工程骨架
```

每个功能分支一个主题，`--no-ff` 合并留下合并节点（历史上能看出"这是一整个 P0"）。commit 信息用约定式前缀：`feat:` / `docs:` / `fix:` / `test:`。本地仓库暂无远端；推 GitHub 时在平台上把 main 设为保护分支（禁止直推、必须 PR），流程即闭环。
